# КР2 --- план разработки JavaFX-приложения

> Общий рабочий документ команды из 4 человек. Используем его как
> источник договорённостей по задачам, интеграции и проверке результата.
> Имена участников пока не указаны --- замените «Участник 1--4» на имена
> команды.

## 1. Цель проекта

Доработать проект КР1 до настольного JavaFX-приложения для работы с
заявками IT-OUTSOURCE и пользователями. Приложение должно подключаться к
PostgreSQL через JDBC и предоставлять GUI для просмотра, добавления,
редактирования, удаления, поиска, фильтрации, сортировки, просмотра
статистики и экспорта данных.

**Главный принцип:** не переписываем рабочую бизнес-логику КР1 без
необходимости. Переиспользуем существующие модели, сервисы, репозитории
и схему PostgreSQL. Добавляем JavaFX-представления, FXML, контроллеры и
CSS.

## 2. Текущий контекст КР1

Текущая архитектура:

`ConsoleUI → Service → Repository → PostgreSQL`

Основные части проекта:

-   `model`: `User`, `ServiceRequest`, перечисления ролей, статусов,
    категорий и приоритетов;
-   `service`: `UserService`, `ServiceRequestService`,
    `ExcelExportService`;
-   `repository`: `CrudRepository<T>`, `UserRepository`,
    `ServiceRequestRepository`, `JdbcServiceRequestRepository`;
-   `util`: `DatabaseManager`;
-   `ui`: текущий `ConsoleUI`;
-   `sql`: схема БД, создание БД, начальные данные и миграция;
-   `exception`: `BusinessException`, `EntityNotFoundException`,
    `DatabaseException`.

Основные сущности: пользователи и заявки. Роли: `CLIENT`, `EXECUTOR`,
`ADMIN`. Статусы заявок: `NEW`, `IN_PROGRESS`, `WAITING`, `RESOLVED`,
`CLOSED`. Приоритеты: `LOW`, `MEDIUM`, `HIGH`. Категории: `HARDWARE`,
`SOFTWARE`, `NETWORK`, `CONSULTATION`.

Перед началом разработки каждый участник должен получить актуальную
версию репозитория и проверить существующие сигнатуры методов. Не
предполагать, что методы называются именно так, как описано в этом
документе: сверяйтесь с кодом.

## 3. Технические договорённости

-   GUI: JavaFX, FXML и CSS.
-   Слои:
    `FXML/View → Controller → Service → Repository/DAO → PostgreSQL`.
-   Контроллеры не содержат SQL и не реализуют бизнес-правила --- они
    вызывают сервисы.
-   Для таблиц использовать `TableView`; для обновления данных ---
    `ObservableList` или эквивалентный управляемый список.
-   Связанные сущности выбирать через `ComboBox`/`ListView`, а не
    вводить вручную числовые ID.
-   Для удаления показывать подтверждение.
-   Ошибки показывать пользователю понятными сообщениями; не показывать
    stack trace.
-   Настройки подключения брать из конфигурации, не хранить пароль в
    исходниках и не коммитить локальный `db.properties`.
-   Не оставлять кнопки и обработчики, которые ничего не делают.
-   Сохранять существующую схему БД, если изменение не согласовано всей
    командой и не требуется формальным заданием.

### Важное решение по версиям

В требованиях преподавателя указаны **Java 21**, **Maven 3.9+** и
**Docker** для запуска/проверки демонстрационного стенда. Проект настроен на
Java 21; всем участникам нужно использовать JDK 21 для сборки и запуска.

Docker-стенд преподавателя и собственное JavaFX-приложение ---
разные вещи: наше приложение продолжает подключаться к PostgreSQL
проекта через JDBC, если требования КР2 не предписывают иного.

## 6. Порядок разработки и интеграции

1.  **Общая синхронизация.** Все обновляют репозиторий и изучают текущие
    модели/сервисы/репозитории.
2.  **Java 21.** Все участники используют JDK 21 для сборки и запуска.
3.  **Каркас.** Участник 1 поднимает минимальное JavaFX-приложение,
    FXML, CSS и навигацию.
4.  **Согласование контрактов.** Участники 2--4 фиксируют имена FXML,
    контроллеров, методы сервисов и способ перехода между экранами.
5.  **Параллельная разработка.** Участники работают в отдельных ветках и
    не редактируют один и тот же файл без предварительной
    договорённости.
6.  **Ранняя интеграция.** Каждый регулярно вливает небольшие
    завершённые изменения в общую ветку через review, а не приносит всю
    работу в последний день.
7.  **Общая проверка.** Запустить приложение с чистой/подготовленной БД,
    проверить CRUD, ошибки, фильтры, статистику и экспорт.
8.  **Репетиция защиты.** Каждый участник должен уметь объяснить свою
    часть и общую архитектуру.

## 7. Git и правила командной работы

-   Основная ветка: `main` (или согласованная командой защищённая
    ветка).
-   Для задач создавайте отдельные ветки, например:
    -   `feature/javafx-shell`
    -   `feature/requests-ui`
    -   `feature/users-search`
    -   `feature/statistics-export`
-   Делайте небольшие коммиты с понятными сообщениями.
-   Перед началом работы обновляйте свою ветку относительно общей.
-   Перед слиянием проверяйте diff и запускайте сборку/тесты в доступном
    окружении.
-   Не коммитьте `db.properties`, пароли, локальные настройки IDE и
    временные файлы.
-   Не меняйте общие сервисы, модели, SQL-схему и `pom.xml` независимо
    от команды.
-   Если для GUI не хватает метода в сервисе, сначала обсудите изменение
    с владельцем соответствующей части.
-   Не исправляйте чужую часть молча: создайте issue/сообщение или
    согласуйте изменение.
-   При конфликте приоритет у согласованного контракта; конфликт решают
    авторы затронутых частей вместе.

## 10. Важные ограничения текущей реализации

-   В текущем КР1 нет полноценной авторизации по паролю; не обещать
    преподавателю наличие логина/пароля, если это отдельно не
    реализовано и не требуется.
-   Не считать, что роль `ADMIN` автоматически имеет специальные права:
    проверяйте реальные правила в сервисах.
-   Не добавлять историю комментариев, SLA, мягкое удаление или другие
    новые функции без прямого требования.
-   Существующие правила изменения статусов, редактирования и оценки
    должны оставаться в сервисном слое.
-   Если валидация GUI и сервисная валидация отличаются, сервис остаётся
    источником бизнес-правил; GUI может проверять ввод заранее для
    удобства пользователя.
